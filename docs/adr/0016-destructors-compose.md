# A field's destructor runs from its parent's, and the compiler generates the parent when there is none

If a struct has a field whose type has a destructor, that destructor is called from the parent's
destructor. If the parent declares no destructor, the compiler generates one. `has_destructor` already
exists on the semantic type (`src/types/StructType.hpp:32`), so `compiler.structs.has_destructor` lets a
library ask whether cleanup already runs for a type.

The corpus states half of this and leaves half open. `deeptest2.fin:45-46` gives the generate-when-absent
half outright — "basic destructors are generated by compiler by default but you can overwrite it" — while
the recursive half was undetermined, because the file's only destructor is an override that deletes its
fields by hand. That is consistent with composition and does not establish it. This decision establishes
it.

## Why this is a language rule and not a library's job

It decides how much weight the event system has to carry. With composition, `variable_scope_exit` fires
once for the outer variable and the nested cleanup is the language's own work. Without it, a handler must
walk the whole field tree itself — and walking a tree needs a loop, which ADR 0006's line refuses. So
declining composition would not merely move work into libraries: it would reopen the interpretability
line and spend the no-hang guarantee to do it.

D reaches the same rule by the same route, and gets most of its use-site-free cleanup behaviour from this
plain language rule rather than from any metaprogramming facility. That is the shape worth copying: the
cheap mechanism carries the common case, and the expensive one is left for what actually needs it.

## Consequences

Field destructors run **after** a declared destructor's body, as in C++ and D, rather than being
suppressed by it. A user who declares a destructor and forgets a field does not leak.

That interacts with one corpus construct and the interaction is left open deliberately. `deeptest2.fin`'s
`~Person()` writes `delete &name; delete &age;`, which is explicit deallocation of storage and not a
destructor call, so it does not collide with automatic field cleanup as things stand. If `delete &field`
is later specified to invoke the field's destructor, it collides directly and produces a double free, and
this decision is the one to revisit — not that one.

A generated destructor is observable: `compiler.structs.has_destructor` answers true for a type that
declared none but acquired one by composition. A library asking "does cleanup run for this type" wants
that answer, and a library asking "did the user write a destructor" is asking a different question and
needs a different operation. Only the first is committed to here.
